# Workflow

- Never ask the user to paste a PAT or token into the conversation. The accepted path is: remove the stale credential from GCM, then let the next `git push` trigger GCM's device/browser login, which authenticates the correct account with no secret ever entering the transcript. Confidence: 0.9
- Before touching shared or machine-wide state (e.g. logging an account out of Windows Credential Manager, which affects every repo on the box), state the blast radius explicitly and ask which approach to take. The user engaged with the options rather than dictating a method. Confidence: 0.8
- After a fix like an auth change, verify which identity actually authenticated (`git-credential-manager github list`, remote ref state) instead of treating a successful push as proof — a stale shared credential can make a push succeed as the wrong user. Confidence: 0.85
- When a fix has a scope the user didn't ask for (machine-wide effect, files changing that belong to agent internals), say so plainly in the summary even if the headline task succeeded. Confidence: 0.75
- For a large change, read every source doc, dispatch a thorough explore subagent for an inventory, then write one phased plan with a concrete "done when" gate per phase *before* touching code. Confidence: 0.85
- Establish the build + test baseline before the first edit and state the numbers, so a pre-existing failure is never mistaken for a regression later. Confidence: 0.9
- After plan approval: cut a feature branch, then execute phase by phase with a build+test gate and a separate commit per phase, so any break is attributable to one phase. Confidence: 0.85
- Never trust a subagent's "unused/dead code" verdict on its own — grep the import paths before deleting. In this session the explorer wrongly marked `components/agents/` and `TodoList` as dead when `ChatPage` imported both. Confidence: 0.9
- Use `git rm` for file and directory deletions so the removal is staged and visible in the diff. Confidence: 0.8
- When `edit_file` won't match inside a very large file (hundreds of lines), stop fighting the anchor: write a short Python splice script (locate start/end markers, replace the slice) into a repo-local `.scratch/` directory, run it, and gitignore `.scratch/` so the helper never lands in a commit. Confidence: 0.85
- After a botched edit, re-read the exact region before retrying. A near-miss `edit_file` that "succeeds" by matching a different line can delete an unrelated declaration silently. Confidence: 0.8
- During a long run, report short checkpoints — branch, commit count, what's done, what remains — so progress is visible without interrupting the work. Confidence: 0.8
- **Prove the reference survived adaptation with a two-bucket close-out: "kept exactly as the block ships it" enumerated item by item, then "tweaked — data and wiring only" per region.** The byte-identical `diff` proves the reference was intact *before* the second pass; on its own it says nothing about what the adaptation did to it. Listing the untouched items concretely (`Sidebar collapsible="icon" variant="inset"`, `h-14` header, the group/menu structure, the 12px muted labels, the chevron rotate, the footer card, all tokens/spacing/radii/motion) and then naming each changed region and exactly what changed there — menu manifest, top bar, account, content wrapper, sidebar actions — is what lets the user tell a scoped data swap from a quiet rewrite. This is the verification the "install then tweak" sequencing needs at the *end*, since the diff evidence is stale once you've edited. Confidence: 0.8
- **Render the UI and look at it.** A green typecheck/build/test gate does not catch runtime crashes, missing providers, silent render branches or contrast failures. Three real bugs in this redesign were invisible to the build and only surfaced in a browser: `Tooltip` outside `TooltipProvider` (whole app was an error screen), empty-state copy that never rendered because `React.Children.count` counts a trailing `undefined` (use `Children.toArray`), and a text token at 3.02:1 contrast. Treat "the build is green" as necessary, not sufficient — get pixels on screen before declaring a phase done. Confidence: 0.9
- When the user has been told the app can't be visually verified, and a way to fix that exists, offer it and get a decision rather than silently continuing on a weaker gate. The honest framing that landed: naming the specific gap ("I can prove tokens and utilities exist, but not that the board *looks* right"), then asking. Confidence: 0.85
- Run `agent-browser a11y` (axe-core) as a standing gate on any UI phase, and check **both themes** — contrast pairs behave differently per theme. Fix violations and re-run until zero rather than triaging. Confidence: 0.85
- Verify contrast numerically, not by eye: compute the ratio from the hex values in a browser `eval` so the finding is a number against the 4.5:1 bar. Keep a tightest-pair watchlist (here `ink-3` on `surface`, and `ink-4` which is non-text-only and fails at 3.02:1). Confidence: 0.8
- **When an axe contrast flag disagrees with your own measurement, believe axe and find out why — the parent you assumed is behind the text is usually not the parent that is.** `text-success` measured 5.02:1 on white (passing, so the obvious "fix" would have been wrong and left the bug in place) but axe still flagged it. Walking the ancestor chain for the first non-transparent `backgroundColor` found `bg-well` (`#eef1f6`) several levels up, where the real ratio was **2.54:1**. Script the walk in one `eval` — query every element matching the class, report own colour, parent background, and the ancestor chain — instead of guessing at the surface. A ratio that "should" pass and doesn't means your background model is wrong, not that the tool is. Confidence: 0.9
- A documented "non-text only" token being used for real copy is a spec violation at scale, not a few stray call sites: `text-ink-4` was on body text in **60+ places** across one feature while measuring 3.0:1. Grep for the offending token feature-wide, and treat a "one instance" reading as evidence the grep is scoped too narrowly. Also sweep the legacy `var(--color-*)` aliases to the current `var(--c-*)` in the same pass — the aliases still resolve, so they hide from a typecheck, but they are one indirection away from the palette and are exactly where drift accumulates. Both sweeps are scripted (`.scratch/*.py`, idempotent, run with `python`) since the hand-typed list of hue replacements is long and repetitive; `npx tsc -b` after each sweep is the gate. Confidence: 0.85
- Typecheck cannot see a design-system violation. The board-wide `ink-4` misuse, a 2.54:1 contrast pair and four `h1 → h3` heading jumps were all invisible to `tsc -b`, `pnpm test` and `pnpm build` — they surfaced only from `agent-browser a11y` and a screenshot. When a phase claims "port this to the current system", the port itself is the deliverable and the audit is what proves it. Confidence: 0.85
- Give a **state that drives a decision its own semantic hue, distinct from the accent.** Review was sharing violet chrome inherited from an older system; the fix was dedicated `--c-review` / `-text` / `-tint`, on the argument that review is the state the gate acts on, so it has to be findable without reading the label — and the accent stays reserved for interactive/selected/primary action. Reuse of the accent for a status is what makes a system drift. Confidence: 0.8
- **Replace a generic action dropdown with explicit buttons when the options differ only by a hidden side effect.** The review gate's "Choose an action…" select made the user guess what *Commit* versus *Commit & Push* did; three labelled buttons (Mark done / Commit / Approve and push) say it outright. Also make the primary label reflect the current selection — a partial commit reads "Commit 3", not a vague "Approve" — and keep a disabled state where the action is genuinely unavailable (Commit disabled at 0 files selected). A dropdown is fine when the options are genuinely a taxonomy; it is a smell when it is a set of buttons that happen to share a trigger. Confidence: 0.8
- A sticky action bar is the right home for a decision that must always be reachable: the review gate sits `sticky bottom-0` at the foot of the diff column with counts on the left and actions right-anchored by `ml-auto`, so the approval is never scrolled off. Pair it with a `role="alert"` error strip above the row so the failure names what actually failed (here a backend Windows path bug, surfaced honestly rather than as a generic failure toast). Confidence: 0.8
- A real error in a data view is worth surfacing rather than hiding behind an empty state. The review section's error banner sits above the action bar instead of replacing the panel, so the user can still read the diff and the controls stay reachable while the failure is explained. Confidence: 0.75
- Make file-selection state legible as a live count, not as static instructional copy: the "Commit adds only checked files" sentence was replaced by a running "3 of 9 selected" that updates as boxes are ticked, and the default is to select everything once the diff first arrives so the common case is one click rather than a select-all first. Default selection to the common case, then make the deviation visible. Confidence: 0.8
- A `text-2xs` (11px) label is *not* large text for contrast purposes — it needs the full 4.5:1, so small stat labels are where a mid-palette semantic colour fails first. Check the smallest text in a component, not the representative one. Confidence: 0.8
- Section-level headings under a page `h1` must be `h2`. Four `h3`s in the task-detail page (Section title, Runtime status, Discussion, Agent progress) all jumped a level; axe caught the first one and a `grep "<h3"` over the feature found the rest. When fixing a heading jump, grep the whole feature for the same tag rather than fixing the one the audit named. Confidence: 0.85
- Never let colour be the only signal in a diff gutter: the `+`/`−` glyph repeats the green/red, so the file summary (`+12 −3`) and the line markers agree. Style says this and the diff view is where it matters most. Confidence: 0.8
- Vite's dev server serves a **cached page** after a token/class sweep — `agent-browser a11y` returned byte-identical results after a real change, because the page was still the old one. `location.reload(true)` (a hard reload) forced the re-audit. If an audit reports exactly the same findings after you fixed them, suspect the cache before suspecting your fix. Confidence: 0.8
- Colour-only sweeps should end with the grep that proves the sweep: after the board sweep, re-running the same `text-(violet|amber|emerald|sky|rose|red)-[0-9]` pattern returned nothing. Report the empty grep as the evidence, and note in the summary that hand-mixed Tailwind status hues are the tell that a page is off-system. Confidence: 0.8
- When a token sweep reveals the same class of bug in files not yet swept, say so and name the likely source rather than quietly fixing each file. "The 60+ `ink-4` cases and the violet/amber drift suggest the same problem exists in Chat, Overview, Knowledge — I'd rather fix it at the source than repeat these per-file corrections" is the framing that surfaces the systemic issue. Naming the pattern earns agreement for the bigger fix. Confidence: 0.8
- **A fill token is not automatically a text token — this holds for every semantic hue, and for sunken fills as well as tints.** The solid `--c-accent` on its own `--c-accent-tint` measured 4.49:1, just under the 4.5 floor for the 13px active nav label. The fix is a separate text-safe sibling per hue (`--c-accent-text`, then `--c-success-text` / `--c-warning-text` / `--c-review-text` once the same pattern turned up elsewhere), used wherever that colour is *text* on any fill; the solid value stays for icons, borders and large numerals. A later pass found solid success on `bg-well` at **2.54:1** — a sunken background is no safer than a tint. So: measure, and when a hue-on-hue ratio lands under 4.5, add the `-text` variant rather than reaching for font weight or a darker tint. Then grep for every tinted/sunken call site and migrate them together — three accent sites, and several success/danger rows, shared the same latent failure. Confidence: 0.9
- **Font weight does not change a contrast ratio.** Reaching for `font-medium` to satisfy an axe contrast flag is a guess; compute the composited ratio from the live `getComputedStyle` colour values, and if it lands at 4.50 it is a token problem, not a weight problem. Say so in the token comment so the next pass doesn't try the weight trick again. Confidence: 0.8
- **Decorative ground textures are only as good as the blur behind them.** A `dot-grid` of 1px dots at a 22px pitch under a sidebar with `backdrop-filter` is averaged by the blur into a flat haze — the glass has nothing left to diffuse, which is the exact failure `smoke-wash` was introduced to prevent. When swapping a shell ground, ask what scale survives the blur and check that the surface behind the glass is actually visible. The replacement needs a **real falloff curve** (an extra midpoint stop so each bloom ramps 0 → peak → 0 rather than running at full strength then cutting to nothing) or it reads as paint instead of emission, and dark mode needs its own stronger alphas or a near-black canvas swallows it. Leave the original texture where nothing blurs over it. Confidence: 0.8
- **Verify a CSS/design change against rendered pixels in both themes, not only against compiled CSS.** `pnpm build` + `grep -o '\.glow-ground{[^}]*}' dist/assets/*.css` proves the utility was emitted and the `.dark` override survived Tailwind's cascade; it does not prove it *looks* right behind glass. Serving the build and screenshotting light and dark is the gate that catches the value being wrong. Confidence: 0.85
- A swap that changes a shared ground material is not finished when the components are edited: grep every consumer (`grep -rn 'dot-grid'`) and update the ones whose comments still describe the old material, and write the reasoning plus the contrast proof into `design.md` so the choice survives the next pass. Reporting which surfaces kept the old texture and why is part of the deliverable. Confidence: 0.8
- A design utility's comment should carry the **rejected alternative and the reason it lost**, not just what the utility does. The 0→peak→0 curve note, the measured contrast numbers, and "a regular lattice reads as graph paper" are what stop a later pass from re-introducing the tint it replaced. Confidence: 0.75
- `pnpm build` and the test suite are the necessary gates on a CSS change, but neither can see a design regression — `pnpm build` + `pnpm test` (39 passing) both went green while the ground behind the sidebar was still the wrong texture. Get pixels on screen before declaring the swap done. Confidence: 0.8
- Seed realistic data before judging a screen. Empty states and populated states are different layouts — create sample records across every status, then screenshot. Confidence: 0.8
- **A settings control that renders is not a working control.** For each one, click it and assert the *effect* in the DOM and in storage, not the button's appearance: Theme → `documentElement.className` plus computed `body` background; Density → `data-density` plus the CSS variable it was supposed to move (`--card-pad` 12px→10px); Motion → `data-motion`. Also confirm it survives a reload, then **reset the values you changed** so the next screenshot isn't taken in a state the user never set. Confidence: 0.85
- When a browser click doesn't land, suspect your selector before the component: `find text "Compact"` hit the wrong element, while `find nth 4 "[role=radio]"` hit the right one. Reach for the structural role selector (or a snapshot `@eN` ref) rather than re-phrasing a text selector, and re-check the DOM before editing code. Confidence: 0.8
- When a large refactor moves code out of a god file, report the before/after line count as proof the extraction achieved its goal. Extend the proof to the *inverse* claim: pages rewritten onto shared components should come out **smaller despite gaining functionality** (Providers 8.6→8.1kB, Skills 6.5→3.9kB), and quoting the byte/line deltas is what shows the abstraction earned its place rather than just adding a layer. Confidence: 0.85
- Deleting a component can silently remove a provider or side-effect mount that other code depended on. After any large deletion pass, re-check that cross-cutting providers (`TooltipProvider`, theme application, error boundaries) are mounted at the app root rather than inside a deleted subtree. Confidence: 0.8
- Anything created while working on the user's own machine or data (test tasks, dev credentials used, mock servers) gets disclosed in the summary with an offer to clean it up — the user was told six test tasks were added to their `local` board and that a seeded dev password was used. The rendered-verification case generalizes it: an isolated `HERMES_HOME`-scoped server instance on its own port was started for screenshots, and the close-out named the port, the seed password, that the live instance was left untouched, and that both were stopped with their ports released. Confidence: 0.85
- The user works from a pre-existing `index.html` theme script as well as a React `applyTheme()`. When changing which theme is the default, fix **both** and note in both that they must stay in sync — the inline pre-paint script runs first and will fight the app otherwise, silently. A dead theme toggle looks exactly like a CSS specificity bug. Confidence: 0.8
- When renaming a whole token family (e.g. `--c-lantern*` → `--c-accent*`), finish the rename with a repo-wide grep for the old name and treat an empty result as the gate — then check the served/compiled CSS too, since a stale dev transform will fake a failure. Keep legacy `@theme` aliases wired to the new values so unmigrated components keep rendering. Confidence: 0.85
- Sweeping a palette change means checking that the accent never collides with a semantic/status colour. One accent carrying brand, focus, selection *and* status at once is the failure mode to design against: give every status its own hue and reserve the accent for "interactive / selected / primary action". Say so in the spec. Confidence: 0.8
- Concretely: **at most one accent-filled forward action per screen** (e.g. the page's "New task" button). Nav/selection state must not also wear the accent — a selected nav row lifts off the canvas with a raised fill + 1px border + hairline shadow instead, so the single accent action stays the loudest thing on screen. An accent tint repeated on every active row is what makes a shell read as noisy. Confidence: 0.85
- Give the agent room to call out a pattern as wrong even when the user just asked for a closer copy. Offering "this is a genuine design correction, not just a copy" alongside a one-number check, when it holds up, is the way to surface a real design lesson instead of silently doing what was asked. Confidence: 0.75
- **A hand-written WCAG luminance function must linearise sRGB first** (`v <= 0.03928 ? v/12.92 : ((v+0.055)/1.055)^2.4`). Omitting it collapses every ratio toward 1.0 and makes a palette that actually passes look broken — when a whole table reads near-unity, suspect the formula before the colours. Pick the bar by what the colour does: 4.5:1 for hues that carry text in a label, 3.0:1 for genuinely non-text marks (a 2px status-lamp track, a border). Verified here: softened pastel status labels 5.08–12.95 against a 4.5 bar, lamps 3.20–11.56 against 3.0. Confidence: 0.85
- **Check contrast against the worst-case background the theme can produce, not the nominal surface.** An ambient tint, a smoked/photographic canvas or a dot-grid panel changes the background behind the text, and that is where a palette silently fails. Sweep a range of tinted canvas values and report the worst case per ink level — body text held 8.54:1 and tertiary ink 5.40:1 across a heavily washed canvas, which is the number that makes a decorative background safe to adopt. Confidence: 0.8
- After picking new token values, verify the claimed contrast ratios before writing them into a code comment, and correct the comment when the measurement disagrees with the guess. A comment asserting 5.24:1 that actually measures 5.15:1 is worse than no comment. Confidence: 0.8
- Before reimplementing an existing component, read its source to learn what it actually is rather than what its name implies. `Logo` was assumed to be wordmark-only and turned out to be the whole lockup — a wrong assumption cost two debugging round-trips. If a rendering looks wrong, scale the element up in the browser and look at it before theorising. Confidence: 0.85
- **When the user says the result still doesn't match the reference, stop tweaking and measure.** A structurally-correct-but-eyeballed rebuild gets sent back; the fix is to open the live reference in a browser, read the actual computed values off the DOM (row height, inset, font size, divider, fill, radius, header height, container width), rebuild against those numbers, then measure the local build the same way and report a reference-vs-mine table. Screenshot comparison is what produced the rejected pass. Confidence: 0.85
- If measuring the deployed reference still doesn't produce a match, go up a level: when the user supplies the reference's **repository**, clone it and read the real source files (component + CSS tokens) instead of probing the live DOM again. Computed-style probes misattribute properties — a `border-bottom` read off a nav row actually belonged to its parent — which is how two rounds of confidently wrong claims happened. Source beats measurement beats screenshot. Confidence: 0.9
- Keep a reference clone in the gitignored `.scratch/` directory and tell the user its path, so a follow-up "port this too" can be served from the same checkout without re-cloning. Confidence: 0.8
- When wrapping existing pages in a new app shell, the shell should own the document's landmarks — one `<main>` — and page components must stop rendering their own. A duplicated `<main>` is an axe landmark violation, not a style smell, and only surfaces after the shell exists. Confidence: 0.8
- After a faithful port, state plainly which parts were deliberately *not* taken and why (e.g. an account card would mean inventing an identity the product doesn't have). Naming the omissions and the reasoning is welcome; silently dropping them is not. Confidence: 0.8
- Commit per revision checkpoint, not per tiny fix, and let the commit message carry the full rationale including what the reference contributed and what was deliberately left out. The "before/after" table of tokens (old value → new value → why) is the part the user reads. Confidence: 0.8
- **A ported block's demo data gets re-derived from the app's own model — but only in a second pass, after the untouched block is on screen.** The registry block shipped nav rows with `path` hrefs and invented destinations (`Queue`, `Customers`, `Branding`); this app has no router, so `pagePath()` owns URLs and `Page` owns destinations. The end state is a manifest carrying `page: Page` ids with the shell navigating by id, because a second set of path strings in the manifest is a second source of truth that drifts — write that reasoning into a comment on the manifest so it outlives the port. **But doing this on the first pass is what got the work sent back with "its still not same with the actual app shell".** The user's instruction was "install the applying in app shell then tweak": install verbatim, show it, *then* re-derive the data. Deleting `latest-change.tsx` / `dashboard-skeleton.tsx` / `nav-user.tsx` is right eventually — and when a dropped demo row carried a real function (sign-out) name where it lives now ("still reachable in Settings → Account") — but it is a follow-up pass, not part of landing the block. The order that clears the bar: verbatim install → byte-identical diff proof → adapt only the data layer → retoken. Confidence: 0.8
- **Swapping a primitive that owns its own persistence is a state migration, not a file swap.** Replacing the hand-rolled sidebar with shadcn's `SidebarProvider` meant the collapse preference had to survive: keep the existing `kb-sidebar-collapsed` key, use it as the initial state, and drive the new primitive through its **controlled `open` prop** instead of letting it own a second store. The primitive then keeps persisting to a `sidebar_state` cookie that nothing reads — flag that in the close-out with an offer to strip the write rather than leaving a stray cookie written on every toggle. Add a `window` `storage` listener so two open tabs stay in step, and wrap read/write in try/catch because private mode throws instead of degrading. The same rule holds for any replaced primitive that carries state. Confidence: 0.8
- Every redesign phase must land on the *current* theme and system UI — reuse the established tokens, primitives, focus rings and hairlines instead of styling the new surface ad hoc. The user's go-ahead usually names this constraint ("make sure align with current theme/system ui"), and it means the new work inherits what is already documented rather than renegotiating it. Confidence: 0.8
- Set a wordmark as live text in the UI font; never hand-write SVG glyph outlines for it. Fabricated path data renders as plausible-looking nonsense ("Switchyard" came out as "FNRVVELN") and a clean typecheck does not catch it. The reference sets its own name as text too. Confidence: 0.85
- Punch holes in an SVG mark with a `<mask>`, not by filling them with a theme colour variable. `fill="var(--c-surface)"` resolves against the page rather than the mark, so the eyes vanished and the octopus rendered as a solid blob; a mask stays correct on canvas, on a card and on the sign-in surface. Confidence: 0.8
- Judge a logo/mark at the sizes it will really be used and in both themes before committing — a throwaway HTML preview showing it at 16/20/24/32/64px in light and dark is faster and more honest than squinting at it in situ. Then record the legible minimum size in the design doc, so a later pass doesn't quietly shrink it below legibility. Confidence: 0.8
- Run `agent-browser a11y` on an **idle** page: dismiss any open dropdown/menu and press Escape first. An open Radix menu puts the rest of the document in a modal state and produces phantom landmark and heading findings. Re-run once the surface is closed, then treat what's left as the real list. Confidence: 0.8
- **An a11y finding is a hypothesis until you check the DOM.** axe reported "no h1" on Providers right after a chained `open … && a11y` — the audit ran mid-navigation while the SPA was still mounting. An `eval` reading `document.querySelectorAll('h1')` proved the page had rendered fine. Re-run the audit on a settled page before touching code, and say in the summary that the finding was a timing artifact — reporting a non-bug as fixed (or half-fixing it) is worse than the false positive. Confidence: 0.8
- Screenshot the page in its **current** state before rewriting it, so the comparison is honest, then report a removed → now table in the summary. "The current state is the baseline" framing makes the redesign legible instead of an unverifiable claim. Confidence: 0.8
- Before rewriting a file that has a test file, read the test first and treat the tested export as a contract: `groupWorkspacesByPlatform` had six tests over the local/loopback bucket and drive-letter inference, so it was left byte-identical and only the presentation around it changed. Run that specific suite as the gate, and say in the commit message that the logic was deliberately untouched. Confidence: 0.85
- Colour only what is a **state**. Platform, transport and OS were three separately tinted badges (violet ssh, sky windows, amber linux) and collapsed into one line of plain text — they are context, not state, and tinting them put three competing hues on every card. The inverse also holds: don't spend a semantic colour on decoration, or the colour stops meaning anything. The ping trace was drawing in success green when green is reserved for the confirmed `done` status; charts and neutral marks draw in ink. Confidence: 0.8
- Show a status message only when it's a problem. A healthy `"path ok"` rendered in danger-text on every card was pure noise — failures surface in full, healthy ones move to the tooltip. Confidence: 0.8
- Never hardcode a colour literal in an inline `style` (a status chip had `rgba(0,0,0,0.2)` baked in, which read as a dark blob on the light theme). It fights the other theme and escapes class-level greps, so it survives a sweep for hand-mixed status colours. Confidence: 0.8
- Don't nest interactive controls. A `role="button"` span sitting inside the disclosure `<button>` is valid to the compiler and invalid to a screen reader; axe flagged it as `nested-interactive`. Make the inner action a real sibling `Button` with its own label, and if a state lamp can't be seen against its background, bump its tone — an invisible lamp isn't communicating state. Confidence: 0.8
- For genuinely tabular data, use a real `<table>` with a `<caption>` and `scope="col"`, not a stack of `article` rows that look like a table. And delete stat tiles that merely restate numbers the table already implies — four decorative cron tiles were pure duplication. Confidence: 0.8
- When a rendered control disagrees with what was asked for, verify the underlying state in the DOM (`aria-checked` / `data-state` via `agent-browser eval`) before assuming a UI bug. A cron job created with `enabled: false` came back enabled: that was backend behaviour, not styling, so it was reported as a flag rather than patched in the frontend. Confidence: 0.8
- When a shared primitive supersedes a pattern, grep for the old hand-rolled version and migrate every call site before moving on (here `system-modal|fixed inset-0 z-50 …` for overlays). Assign one surface per purpose — Dialog for short forms and confirmations, Sheet for viewing/editing an entry — so the app ends with exactly one dialog system. While in a primitive file, port it fully to the current system (300/500ms `ease-in-out` → 240ms on `--ease-out-expo`, 50%-black scrim → 2px blur, 1px borders → 0.8px hairlines) and record the change in the commit message. Confidence: 0.8
- Check the **document outline**, not just the styling, in reusable components. A list-card title sitting directly under the page `h1` must be an `h2`; an `h3` there is a heading-level jump that only axe catches. Confidence: 0.8
- Establish a new shared pattern on **one real page first** (Profiles as the reference), prove it renders and audits clean, commit, and only then apply it to the remaining pages — the other densities get validated against a shipped precedent rather than in parallel. Then close the loop by applying it everywhere the pattern claims to cover, and treat that as the real test: "one anatomy, different hierarchy" is only earned when every density (identity / infrastructure / registry) is shipped and visibly still the same component. Say that explicitly in the summary rather than leaving it as a slogan. Confidence: 0.8
- When composing a filter + search list, apply **every** filter before short-circuiting on the empty search box — `if (!needle) return list` must come after the other filters have run, or a chip-filtered view silently reappears the moment the search clears. Cheap to get wrong, invisible until a user types then deletes. Confidence: 0.8
- When a screen explains an action in prose, make it a control. Three sentences of Indonesian instructional text about linking a provider to a profile were a `Select` with a real label, a placeholder that reflects the current state, and `aria-label` — a disabled control that explains itself beats a paragraph next to a control, and it localises for free.
