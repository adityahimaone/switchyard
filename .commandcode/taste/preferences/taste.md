# Communication

- Writes short, informal, mixed-language messages (e.g. "cek why my github change to imamdevops can you change to user adityahimaone") — treats "cek" as "check". Interpret the intent and act; do not ask for clarification when the request is recoverable from context. Confidence: 0.8
- Phrases requests as "can you change X to Y" — expects the change to be made, not a menu of options. Lead with doing the work; ask only when a decision is genuinely the user's to make (irreversible, credential-, or scope-affecting). Confidence: 0.75
- When given the option to run a command themselves via the `!` prefix, the agent should be willing to hand over the exact command lines rather than force interactive logins through its own non-interactive shell. Confidence: 0.7
- Prefers summaries that state plainly: what was actually wrong (not the assumed cause), the fix applied, verification performed, and any remaining state. The corrective framing "your identity was never X — this is authentication, not identity" landed well. Confidence: 0.8
- Appreciates being told about side effects the user did not ask for (machine-wide credential impact, tool-owned files changing) in the final summary, with an offer to act on them. Confidence: 0.75
- Requests often arrive as `/<skill-name> <instruction>` (e.g. `/emil-design-eng ...`). Invoke the named skill and honor its framing rather than treating the slash command as decoration. Confidence: 0.8
- "Make sure you execute completely and carefully all docs in ..." signals the whole job should be finished in one run, not a first slice followed by a check-in. Pause for a decision only on genuinely irreversible, scope-affecting, or taste-level choices; everything else is the agent's to decide. Confidence: 0.85
- Likes a brainstorming/plan step before implementation, but expects it to be a *decision record*, not an exploration log: verified ground truth, the questions asked with a recommended option each, and the resulting choice tabulated. Confidence: 0.8
- When a folder already holds detailed design docs plus copy-ready component skeletons, treat those as the specification and execute against them rather than re-inventing the design from scratch. Confidence: 0.8
- Responds to a mid-run checkpoint with a short, unconditional go-ahead ("continue all phase", "continue next sequence") rather than picking among offered options — when a plan is already agreed, re-litigating the sequencing is friction. - Values a checkpoint that admits a real limitation instead of projecting confidence. Confidence: 0.85

It is not an incremental tweak, and a previously approved direction (lantern yellow) gets overturned without ceremony. Confidence: 0.8
- "You can copy all for design app shell and system UI" means structural borrowing, not a literal clone: adopt the reference's shell, density, components and spacing, but keep the product's own colour system, logo, branding and copy. The Switchyard logo reappearing in the header was an explicit requirement. Record in the spec what is deliberately *not* taken and why. Confidence: 0.85
- **"redesign 1:1 based on the prompt, follow all of it including the text/font and etc" widens the fidelity requirement to typography and copy, not just geometry.** Typos and all, but unambiguous: layout, spacing, radii, type scale, font choice and the visible strings are all specified by the reference, so quietly restyling any of them to the house look is a miss. The boundary that still holds is the *token layer* — the reference's default colour values are not the deliverable when the app has its own palette (the install's stock `--sidebar-*` hsl tokens had to be stripped), and demo content is replaced by the app's real destinations. So: 1:1 on everything visible, adapted underneath. Confidence: 0.8
- **"install the applying then tweak" is a sequencing instruction, and it is the whole correction.** He said it plainly after a rejected pass: `pnpm dlx shadcn@latest add @efferd/app-shell-3` — "maybe you not tweak to much in app shell install the applying in app shell then tweak". The order is load, not adapt: install the block, let it sit there unmodified, *look at it*, and only then change things. A first pass that arrives pre-adapted has already made the comparison he was trying to make impossible. The verification for this is mechanical, not a judgement call — keep a pristine copy of the installed files, `diff` it against what is on disk, and report "all 11 block files are byte-identical to the registry" as the proof that the reference is intact before any adaptation starts. Confidence: 0.85
- **"Over-adapted" has a specific anatomy, and each part of it is a separate rejection.** Rewriting the sidebar/header/shell into the project's own shape was refused with "its still not same with the actual app shell". The things that broke fidelity, in order of how visible they were: dropping the block's own demo sub-components (`latest-change.tsx`, `dashboard-skeleton.tsx`, `nav-user.tsx`); relocating every file into a new `app-shell/` subdirectory so the block's own relative imports no longer matched; swapping the block's `path` hrefs for the app's `Page` ids; and retokening the classes to `bg-accent`/`text-accent-ink`/`ink-3`. The rule that lands: in the first pass, change *nothing but what stops it compiling*, and put every adaptation in an explicit second pass. Adapting the data layer is still the right end state — but it comes after the reference is visibly on screen, not before. Confidence: 0.8
