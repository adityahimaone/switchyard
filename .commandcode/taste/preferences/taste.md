# Communication

- Writes short, informal, mixed-language messages (e.g. "cek why my github change to imamdevops can you change to user adityahimaone") — treats "cek" as "check". Interpret the intent and act; do not ask for clarification when the request is recoverable from context. Confidence: 0.8
- Phrases requests as "can you change X to Y" — expects the change to be made, not a menu of options. Lead with doing the work; ask only when a decision is genuinely the user's to make (irreversible, credential-, or scope-affecting). Confidence: 0.75
- When given the option to run a command themselves via the `!` prefix, the agent should be willing to hand over the exact command lines rather than force interactive logins through its own non-interactive shell. Confidence: 0.7
- Prefers summaries that state plainly: what was actually wrong (not the assumed cause), the fix applied, verification performed, and any remaining state. The corrective framing "your identity was never X — this is authentication, not identity" landed well. Confidence: 0.8
- Appreciates being told about side effects the user did not ask for (machine-wide credential impact, tool-owned files changing) in the final summary, with an offer to act on them. Confidence: 0.75
- Requests often arrive as `/<skill-name> <instruction>` (e.g. `/emil-design-eng ...`). Invoke the named skill and honor its framing rather than treating the slash command as decoration. Confidence: 0.8
- "Make sure you execute completely and carefully all docs in ..." signals the whole job should be finished in one run, not a first slice followed by a check-in. Pause for a decision only on genuinely irreversible, scope-affecting, or taste-level choices; everything else is the agent's to decide. Confidence: 0.85
- Likes a brainstorming/plan step before implementation, but expects it to be a *decision record*, not an exploration log: verified ground truth, the questions asked with a recommended option each, and the resulting choice tabulated. Confidence: 0.8
- When a folder already holds detailed design docs plus copy-ready component skeletons, treat those as the specification and execute against them rather than re-inventing the design from scratch. Confidence: 0.8
- Responds to a mid-run checkpoint with a short, unconditional go-ahead ("continue all phase", "continue next sequence") rather than picking among offered options — when a plan is already agreed, re-litigating the sequencing is friction. Raise sequencing questions once, in the plan, then run. This has now happened four separate times, and twice against a closing message that explicitly asked "Which do you want?" / "Chat next?" — offering a menu at the end of a phase does not produce a menu answer, it produces "continue all phase". Don't spend a paragraph on a choice at a phase boundary; state the next phase and run it. Confidence: 0.9
- Values a checkpoint that admits a real limitation instead of projecting confidence. Naming what the verification gap was ("`agent-browser` isn't installed, so I've been checking compiled CSS rather than rendered pixels — that's a real gap") is treated as useful signal, not as hedging. Confidence: 0.85
- When a visual-review option is put to them, picks the concrete setup path (install the tool and check visually) over "I'll review it myself" or "keep going on build gates only" — i.e. prefers the agent own the verification rather than outsource it. Confidence: 0.75
- Detail in the summary is welcome: a table of "what was wrong / why the build missed it" per bug landed well, as did a bullet list of concrete design outcomes ("coupler tick in the status colour, mono summary, Move menu replacing the arrow chips"). Describe what is visibly on screen, not just what changed structurally. Confidence: 0.8
- Signals a design-direction change with a one-liner like "brainstorming again" and expects the whole loop re-run: study the reference, produce a decision record with a recommended option per question, write the outcome into the design doc, then execute in numbered phases. It is not an incremental tweak, and a previously approved direction (lantern yellow) gets overturned without ceremony. Confidence: 0.8
- "You can copy all for design app shell and system UI" means structural borrowing, not a literal clone: adopt the reference's shell, density, components and spacing, but keep the product's own colour system, logo, branding and copy. The Switchyard logo reappearing in the header was an explicit requirement. Record in the spec what is deliberately *not* taken and why. Confidence: 0.85
- When porting a reference she says the main theme stays (e.g. "the main theme still blue") but "other/accent color is up to you" — the primary theme colour is fixed and everything else in the palette is the agent's to decide. Make the call, document it, don't hand the choice back. Confidence: 0.8
- Escalates by handing over more ground truth rather than more adjectives: after a rejected pass she supplied the reference's GitHub repo ("i have fully repository, can you clone it"). A link to the source is a stronger signal than a link to the deployed app — treat it as such. Confidence: 0.85
- Treats `design.md` as the standing record of design decisions — "return in design.md" means the agreed direction is written there before implementation, not only into commit messages. A colour-scheme or shell change is incomplete until the doc reflects it. Confidence: 0.8
- Speaks about a UI that doesn't match the reference in plain terms ("still not same like the image, can you redesign again") and attaches the live reference URL. This is a rejection of the result, not a request for a tweak — it means the previous pass was eyeballed rather than matched, and the next attempt should measure the real reference rather than iterate on the screenshot. Confidence: 0.85
- Names visible surface elements when describing what's off ("the sidebar or app shell") rather than listing structural or token changes — she is looking at the rendered screen, so respond in terms of what is on screen. Confidence: 0.8
- Flagging a pattern the reference has that was deliberately skipped (nested sub-items in the nav) with the cost of adopting it (the manifest would need a `children` array) is welcome — surface the gap and let her decide, rather than adding complexity unasked or silently omitting it. Confidence: 0.8
- Interrupts a long run to raise a visible inconsistency ("we have redundant header in page skills, kanban and etc what a best recommended from you") — she wants **one** named recommendation with the rule behind it and the rejected alternative's cost, not a menu of options and not a silent fix. Lead with the call, then the table, then the check-in. Confidence: 0.75
- Reports layout problems as visible symptoms in plain terms, often with a screenshot ("kanban is overflow and some page has a lot spaces when screen is wide") and an explicit ask for the recommended fix — "what you recommended" signals she wants the diagnosis *and* the chosen remedy in one response, with the diagnosis measured rather than inferred from the image. She is describing what she sees on screen, not naming a CSS property, so the response has to find the cause. Confidence: 0.8
- Treats a cross-cutting shell redundancy spotted mid-run as worth interrupting the run for, rather than deferring it to a later phase. Small inconsistencies in shared chrome get fixed before the feature work continues. Confidence: 0.7
- Her one-liner go-ahead carries the whole brief for the next phase: both the constraint to hold ("make sure align with current theme/system ui") and the pointer to the asset to use ("icon switchyard you can get from mascot-switchyard.png"). Take both as given — go find the named file in the repo and run the phase; don't ask where it is or re-offer a plan. Confidence: 0.8
- When asking for a design rethink, she attaches reference images *and* lists several URLs under a plain `source:` label in one breath — the images are the real brief and the links are a moodboard. Fetch the links, but if they're JS-rendered galleries or turn out to be a different product category (a notes app offered as a dashboard reference), say so plainly and pivot to the images rather than mining them for specs. Don't burn turns extracting tokens from a reference that isn't what she actually pointed at. Confidence: 0.8
- States the target aesthetic in shorthand adjectives plus concrete traits ("modern look 2026", "ditter/dot bg", "smoke transparent", "rounded, font"), and expects you to expand that into real token decisions rather than ask what she means. Interpret the adjectives, propose numbers, and show the contrast proof. Confidence: 0.8
- Gives a scope-limiting goal in plain language alongside the vibe request ("all feature is can sharing ui looks except the content component maybe can different") — the chrome, shell and system UI are meant to be shared across every feature while page content legitimately differs. Read that as a constraint on what goes in the design system, and don't make every page bespoke. Confidence: 0.8
- Likes being told the real tension in a vibe request rather than having it papered over: framing "this is a consumer-app aesthetic and Switchyard is a work tool — adopt the texture, keep data surfaces flat" and flagging that decorative-only means the board looks essentially unchanged were both the substance of the response, not objections to it. Confidence: 0.85
- Mid-run, reports a near-miss honestly rather than quietly leaving it: "I hit an audit false positive worth mentioning… I mention it because I nearly 'fixed' a non-bug." Flagging the tool artefact you *didn't* act on is read as useful rigour, not as noise — it shows the gate is real and that judgement is being applied to it. Confidence: 0.8
