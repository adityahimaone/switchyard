## Session 4: rename opened two surfaces; the rail scope did not follow the room

User report: *"when rename chat its show sidebar and pop up … and still issue in
dynamic title sidebar init title is chat then im click project its change the title
project name and then move to room session the title still project name"*.

### Bug 1 — rename opened a dialog AND a sheet

`ConfirmDialog` keyed off `open={!!sessionAction}`, and `sessionAction` is set for
**every** kind. The rename `DetailSheet` renders on `kind === "rename"`. So renaming
opened both — the sheet (what the user called "sidebar") and the modal ("pop up",
showing *"Choose a title for this room. Renaming does not change its position in the
chat list."* — that whole sentence was the dialog's `description`, i.e. the text the
user quoted).

Worse: the dialog had **no input**, so its `Save title` button could only re-save the
title that was already prefilled. And the rename **sheet had no `footer`**, so there
was no Save button at all — Enter was the only way to commit. The project rename sheet
(next to it) has had a Cancel/Save footer all along, which is how the asymmetry hid.

Fix: the dialog now excludes rename (`!!sessionAction && sessionAction.kind !== "rename"`),
and the rename sheet gained the same footer the project sheet has.

**Rule worth keeping:** a `ConfirmDialog` is for *confirmations*; a `DetailSheet` is for
*edits*. Never both for one action.

### Bug 2 — `onSessionChange` used the project on screen, not the session's project

This was the real defect behind "the title still project name".

```tsx
// App.tsx, before:
onSessionChange={(id) => { setChatRouteID(id); go(activeProject ? `/projects/${activeProject.id}/${id}` : pagePath("chat", id)) }}
```

Two independent faults:
1. It navigated with **`activeProject`** — the project currently open — instead of the
   clicked session's own project.
2. **`go()` only calls `history.pushState`; it never updates `setProjectID`.** So the
   URL and the `projectID` state disagreed after any session click.

Consequence: from inside project A, clicking a **Recents** chat (or a chat in project B)
gave URL `/projects/A/<sid>` and left `projectID = "A"` → the rail title, the composer's
pinned workspace and the project-scoped empty state all named project A for a chat that
is not in it. A reload then landed somewhere different from what was on screen.

Fix (3 files' worth of wiring, 2 files):
- `onSessionChange?: (sessionID: string, projectID?: string) => void`
- `setActive(id, sessionProjectID?: string | null)` — **`undefined` means "caller did
  not say", so keep the page's project** (send / new-chat always create inside it);
  **`null` or `""` means "no project", so leave the current one**. The distinction
  matters: a plain `?? projectID` fallback would have kept the bug.
- `selectSession` passes `item.project_id || null`.
- App: `setProjectID(sessionProjectID)` alongside `go(...)`, so state and history agree.

`ChatSession.project_id` is optional (`project_id?: string`) and the backend detaches
deleted-project sessions with `project_id=''` — hence `|| null` rather than `?? null`.

**Verified by construction, not by running** (no `node_modules`): `ChatPage` is keyed
`activeProject?.id ?? "all"`, so a cross-scope click remounts it, and `sessionID`
initialises from `initialSessionID` (`useState(() => initialSessionID)`) which App feeds
from `chatSessionID = chatRouteID` — so the clicked room opens on the remount. Same-project
clicks keep the key, so `setProjectID(same)` bails out via `Object.is` and there is no
remount or flicker.

### Part 2 — the glass audit: two real problems, both unguarded

Full report: `.workbuddy-ai/audits/2026-10-11-glass-transparency-audit.md`.

**G1 — a genuine WCAG failure.** Light `--glass-tint` at `0.66` put `danger-text`
at **4.36:1** (bar 4.5). Needs **≥ 0.73**; set to **0.74** (worst 4.52:1).
`--glass-tint-strong` `0.82 → 0.86`.

**G2 — BOTH contrast guards were blind. This is the finding that matters.**
- `scripts/contrast-glass.py` had **hardcoded stale values** (0.74/0.84 light,
  0.42/0.78 dark) while the CSS said 0.66/0.82 and 0.52/0.72. It passed every run
  while the token it guarded failed. **Now parses `index.css`, prints what it
  read, and exits non-zero.** Verified: exit 1 at 0.66, exit 0 at 0.74.
- `scripts/token-lint.mjs` **Rule 6 never checked light at all.** It used
  `themeBlock(text, ":root")`, but light's *palette* is in the first `:root` and
  light's *glass fills* are in **`@theme inline`** — different blocks. So
  `cssVar(block,"glass-tint")` → null → empty panel map → the inner loop never
  ran → "success" having measured nothing. **Now each theme names its palette
  block AND its glass block; a missing token is an ERROR, not a skip.** Proven:
  restore 0.66 and the gate now emits `--c-danger-text on light glass-tint …
  4.36:1` (14 → 15 errors).
- `design.md` held a **third** set of values (0.74/0.84, 0.42/0.78, blur 20/32,
  and two `glass-edge` colours matching neither theme). Updated to reality.
- **Block layout of `index.css`, worth remembering:** `.dark` (199) holds dark
  palette + dark glass; `:root` (17) holds the light palette; `@theme inline`
  (345) holds the light glass fills. **`.dark` comes BEFORE the light blocks.**

**G3 — the user's actual complaint: sticky rows cannot occlude.** The three sticky
search rows (`ChatPage` model picker, `ProfilesPage`,
`AttachmentAnalysisSettings`) used `glass-flat-strong` — a tint with **no
`backdrop-filter`** — chosen on the recorded reasoning "blur once per visual
stack, at the panel … rather than an opaque slab pasted over it". That reasoning
missed that the list scrolls *under* the row, so items stayed sharp and read
through it. New **`glass-occlude`** utility (tint + `blur(18px) saturate(1.6)`)
applied to all three. One element = one compositing layer, so it is affordable;
both degradation paths wired.

**G4 — dark hue.** `rgb(46 56 78)` was the tightest choice available: `ink-3` at
4.52:1, *falling* to 4.48:1 by alpha 0.92, because it sits too close to `ink-3`'s
luminance to gain from more of itself. Moved to **`rgb(40 49 68)`** (the hue
`glass-tint-strong` already used) → 4.86:1 at every alpha 0.72–0.92. Alpha
`0.52 → 0.62`. One hue across all three dark tiers now.

**G5 — `token-lint` printed contrast failures as `warn`.** Severity for the
heading came from a second hardcoded rule list written before the `contrast` rule
existed. Now derived from the bucket the finding was pushed into → prints
`FAIL  contrast`.

### NOT a defect — the app header must stay `glass-flat`

`app-header.tsx` is `glass-flat sticky top-0 z-50` and looks like the G3 case. It
is not. Two reasons, both in its own comment: (1) a `backdrop-filter` ancestor
becomes the **containing block for `position: fixed` descendants**, and the
header is nothing but overlay triggers, so a filter would make any un-portalled
overlay position and clip to the bar; (2) nothing scrolls behind it — the shell is
`h-svh overflow-hidden` and scrolling is inside per-page containers, so it sits on
the opaque canvas. **Do not "fix" it.** Also left alone: `glass-flat` buttons and
inputs, segmented/theme-switch pills, and the ~35 `glass-card` sections, all of
which sit on a smooth or opaque ground.
